# Repository Guidelines

## Project Structure & Module Organization
Native Inspect benchmarks are self-contained subpackages (`llm_behavior_eval/<benchmark>/`, modeled on `inspect_template/`) that own their dataset, prompts, solver, scorer, metrics, README, `parity.yaml`, `target_metrics.json` and tests; they never import from each other. `llm_behavior_eval/common/` holds benchmark-agnostic mechanics only (share mechanics, not semantics). `_registry.py` is Inspect's entry point: it discovers every subpackage with a `task.py`, then explicitly registers the opt-in MLflow hook in `hooks/`. `common.target_metrics` merges the per-package target metrics for inspect-brief; there is no root `target_metrics.json`. `presets.py` maps legacy presets to task names and `-T` arguments, and `evaluate.py` is the retired legacy CLI (a migration hint). The legacy engine in `evaluation_utils/` remains only for parity comparison until LLM-171 removes it. Tests live in `tests/` (`tests/test_inspect_<benchmark>.py` per benchmark; reporting in `test_inspect_smoke.py`, `test_inspect_brief.py`, `test_inspect_mlflow.py`, `test_preset_inspect_mapping.py`). Documentation lives in `README.md`, `INSPECT_MIGRATION.md`, `MLFLOW_INTEGRATION.md` and each benchmark's README; runnable examples sit in `examples/`. Do not edit generated `dist/` artifacts.

A benchmark PR adds only its package directory and its own `tests/test_inspect_<benchmark>.py`; do not edit `_registry.py`, `common/` or root files for it. Inspect has one registry per object type and the last registration under a name silently wins, so give every metric, scorer and solver a package-prefixed name (`<benchmark>_metrics`, `<benchmark>_scorer`, `<benchmark>_<step>`); `_registry.py` raises if two modules define the same `llm_behavior_eval/<name>`. Benchmark code, presets, the CLI and the hooks set no inference settings (temperature, top_p, top_k, max_tokens, reasoning/thinking) for the model under test or the grader: users pass them through Inspect per role, and parity runs pass a benchmark's `parity.yaml`. Every Inspect provider must work for either role, including `openai-api/`. See `INSPECT_MIGRATION.md`.

## Build, Test, and Development Commands
- Use Python 3.12 or 3.13 (inspect-brief needs 3.12+; Inspect alone needs 3.11+).
- `uv venv --python 3.12 .venv && source .venv/bin/activate`.
- `uv sync --locked --extra brief --extra mlflow`: the pinned development environment CI uses (it still includes the legacy engine's dependencies).
- `uv pip install --python .venv/bin/python -e '.[brief]'`: editable install; add `mlflow` or `vllm` to the extras as needed.
- The dev container uses Python 3.12 and installs `brief,mlflow` by default; set `LLM_BEHAVIOR_EVAL_INSTALL_EXTRAS` (for example `brief,mlflow,vllm`, or empty for the base package) before `.devcontainer/setup.sh`.
- `pytest`: the full suite (`pyproject.toml` adds `--import-mode=importlib`, which keeps the installed metadata Inspect uses to namespace task names). `pytest tests/test_inspect_smoke.py tests/test_inspect_brief.py` runs every registered task offline on local datasets with mock answer/grader models and checks inspect-brief on the real logs.
- Run `ruff format --check --diff .`, `ruff check .` and `pyrefly check`.
- Run Inspect with the `inspect` command, not `python -m inspect_ai` from the repository root (that drops the `llm_behavior_eval/` task prefix, so inspect-brief applies no targets).
- Prefer `uv`; install into `.venv`, never the system interpreter.

## Coding Style & Naming Conventions
Follow PEP 8 defaults with 4-space indentation. Prefer `snake_case` for modules, functions, and variables; reserve `PascalCase` for classes and `UPPER_SNAKE_CASE` for constants. Keep public options descriptive and aligned with native Inspect task arguments. Let `ruff` fix spacing and import order; avoid disabling rules unless there is a clear justification. Type hints are expected on new public functions—match the patterns in `common/`.

## Testing Guidelines
Add or update `tests/test_*.py` files alongside any new feature. Use `pytest` assertions, fixtures, and `monkeypatch` for mocking (avoid `unittest.mock`). Parametrization keeps dataset scenarios readable. Every benchmark needs registry discovery, dataset conversion and scorer tests, and a run of its registered task on mock answer/grader models that asserts `missing_target_metrics(log.location) == []` (from `llm_behavior_eval.common.target_metrics`): it reads the written `.eval` log the way inspect-brief does, selecting targets by `log.eval.task` and finding each name among the keys of `log.results.scores[*].metrics`. Never compare target names with `EvalMetric.name` or `group`. The cross-benchmark smoke and inspect-brief tests skip a registered task until it has a local dataset fixture and grader verdict in `tests/native_fixtures.py`; add one in a follow-up (the reporting layer owns that file), not in the benchmark PR. Explicitly patch fixture fingerprints; never bypass production CCPC validation. Keep simulated model outputs deterministic so runs remain reproducible. When adding evaluation datasets, include at least one regression test that exercises parsing and scoring logic. Use pytest's `monkeypatch` fixture for patching module attributes and dependencies; create custom fixtures for reusable test setup.

## Commit & Pull Request Guidelines
Write imperative, concise commit titles (e.g., `Add hallu evaluator smoke tests`). Squash trivial fixups locally before raising a PR. Each PR should explain behavior changes, note impacts on benchmark outputs, and link to any tracking issue. Attach screenshots or sample CLI output when the change affects user-visible results. Mark configuration-sensitive updates (MLflow, datasets, prompt presets, target metrics) so reviewers can double-check downstream pipelines.

## Security & Configuration Tips
No secrets should live in the repo. Use environment variables for provider tokens and model paths when invoking Inspect (`HF_TOKEN`, `<SERVICE>_API_KEY`), never task arguments. Verify that large artifacts stay out of version control—`results/` is excluded, so place experimental outputs there and keep them untracked.
