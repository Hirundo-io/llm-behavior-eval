# Repository Guidelines

## Project Structure & Module Organization
The repository is a uv workspace of several distributions sharing the import package `llm_behavior_eval`. The legacy engine (the `llm-behavior-eval` distribution, `pyproject.toml` at the root) lives in `llm_behavior_eval/`, with behavior-specific helpers under `llm_behavior_eval/evaluation_utils/`. Native Inspect benchmarks and their shared code are separate distributions whose directories sit in place inside it, each holding its own `pyproject.toml` (`llm_behavior_eval/common/` is `llm-behavior-eval-common`; a benchmark is `llm_behavior_eval/[<group>/]<benchmark>/`). Tests reside in `tests/` and mirror module names (for example `llm_behavior_eval/evaluation_utils/util_functions.py` ↔ `tests/test_util_functions.py`; a benchmark ↔ `tests/test_inspect_<benchmark>.py`); `tests/example_benchmark/` is a synthetic benchmark distribution used as the template and by packaging tests. Workspace tools live in `scripts/`. Maintained documentation lives in `README.md`, `INSPECT_MIGRATION.md` and `MLFLOW_INTEGRATION.md`, while runnable examples sit in `examples/`. Distribution artifacts generated by releases land in `dist/`; do not edit them manually.

Native Inspect benchmarks follow `INSPECT_MIGRATION.md`: its "Design rules" (self-contained packages; `common` holds only code at least two benchmarks share; no inference settings in code; opt-in `parity.yaml`; the required `grader` role; no credentials in task arguments; pinned dataset revisions; native reasoning parsing with a `judge_sees_answer_reasoning` switch; unreduced metrics and `completion_scorer()` in every task; package-prefixed registry names), "Packaging" (one distribution per benchmark, depending on `llm-behavior-eval-common` and never on `llm-behavior-eval`; no `__init__.py` in namespace directories; an `inspect_ai` entry point named `llm_behavior_eval`) and "Add or migrate a benchmark", whose steps you follow literally: a benchmark PR adds its distribution directory, `tests/test_inspect_<benchmark>.py`, one-line registrations in the root `pyproject.toml` (workspace member, source, dev group, and root or group dependency), its `.github/upstream-revisions.env` entries, and the regenerated `uv.lock`.

## Build, Test, and Development Commands
- `uv sync` (Python 3.11–3.13; `uv.lock` covers the workspace, whose native distributions need 3.11+, while the published `llm-behavior-eval` still installs the legacy engine alone on 3.10.12+): create `.venv` with the whole workspace installed editable (the legacy engine, `llm-behavior-eval-common` and every benchmark distribution; the root in setuptools' `compat` editable mode, see "Packaging" in `INSPECT_MIGRATION.md`) plus the dev tools; add `--extra mlflow` or `--extra vllm` for those integrations. Prefer `uv run <command>` to activating the environment.
- `python scripts/run_package_tests.py [<distribution>]`: run a native distribution's tests in a throwaway environment holding only it and its declared dependencies (`uv run --isolated --no-editable --package <distribution> --with pytest pytest tests/test_inspect_<benchmark>.py`).
- `uv build --all-packages --out-dir dist && python scripts/check_artifact_licenses.py dist`: build every distribution and check its license files; `python scripts/check_installs.py` checks Inspect's task names with wheels, without the legacy distribution, and editable.
- Dev containers run `.devcontainer/setup.sh`, which installs the base project by default; export `LLM_BEHAVIOR_EVAL_INSTALL_EXTRAS="mlflow"` (or `mlflow,vllm`) before invoking the script if you require extras and have sufficient disk space.
- Prefer `uv` for dependency management in automation scripts and local workflows; avoid invoking `pip` directly unless you are installing `uv` itself or a tool explicitly requires `pip`.
- `uv run pytest`: run the full test suite; pass `-k pattern` to scope to a module while iterating.
- Run `ruff format .` (or `ruff format --check --diff` to verify) before committing to ensure consistent styling, followed by `ruff check .` for linting.
- `uv run pyrefly check`: run static type checks with the locked pyrefly (CI uses the same configuration).

## Coding Style & Naming Conventions
Follow PEP 8 defaults with 4-space indentation. Prefer `snake_case` for modules, functions, and variables; reserve `PascalCase` for classes and `UPPER_SNAKE_CASE` for constants. Keep public CLI options descriptive and aligned with existing Typer command names. Let `ruff` fix spacing and import order; avoid disabling rules unless there is a clear justification. Type hints are expected on new public functions—match the patterns in `evaluation_utils/`.

## Testing Guidelines
Add or update `tests/test_*.py` files alongside any new feature. Use `pytest` assertions, fixtures, and `monkeypatch` for mocking (avoid `unittest.mock`). Parametrization keeps dataset scenarios readable. Cover both CLI flows (`llm_behavior_eval/__main__.py`) and factory utilities when behavior changes. Keep simulated model outputs deterministic so runs remain reproducible. When adding evaluation datasets, include at least one regression test that exercises parsing and scoring logic. Every Inspect benchmark test runs its registered task on mock answer/grader models and asserts `missing_target_metrics(log.location) == []`; see "Tests" in `INSPECT_MIGRATION.md`. Use pytest's `monkeypatch` fixture for patching module attributes and dependencies; create custom fixtures for reusable test setup.

## Commit & Pull Request Guidelines
Write imperative, concise commit titles (e.g., `Add hallu evaluator smoke tests`). Squash trivial fixups locally before raising a PR. Each PR should explain behavior changes, note impacts on benchmark outputs, and link to any tracking issue. Attach screenshots or sample CLI output when the change affects user-visible results. Mark configuration-sensitive updates (MLflow, datasets, prompt presets) so reviewers can double-check downstream pipelines.

## Security & Configuration Tips
No secrets should live in the repo. Use environment variables for provider tokens and model paths when invoking `evaluate.py`. Pin GitHub Actions to a commit with the version in a comment; zizmor (`vulnerability-scan.yaml`) checks the workflows. Verify that large artifacts stay out of version control—`results/` is excluded, so place experimental outputs there and keep them untracked.
