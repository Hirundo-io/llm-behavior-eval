# Parameter plumbing audit — config to vLLM runtime, and how each is enforced

Verified by tracing each parameter from its CLI flag / config field to the
actual constructor/call site in the current worktree (branch
`rsch76-prompt-injection-offon-freeze`), and now also classifying **how** it
is mechanically enforced:

- **Library-native**: `llm-behavior-eval` itself validates or asserts this.
- **Wrapper preflight**: `preflight.py` (study-level, outside the library)
  checks this before/without a GPU.
- **Live runtime readback**: `preflight.py` constructs a real engine and
  reads back the resolved value; requires vLLM + GPU, code-complete but
  **not executed** in this freeze (no GPU here).
- **Documented only**: no mechanical check exists anywhere; only recorded in
  this document / Notion.

"Present in a config dataclass" is not accepted as proof of any of the
above; every row cites the file:line where the value actually reaches
`LLM(...)` / `SamplingParams(...)` / `load_dataset(...)`.

## Gaps still disclosed as unresolved (not fixed by adding library machinery, per the "thin wrapper" principle)

1. **No model-revision pin inside `llm-behavior-eval` itself** for the base or judge model (items 1, 2, 8) — closed at the *wrapper* level (`preflight.py resolve-model`, hard-fail on mismatch) rather than the library, since the CLI's `--judge-model`/positional `model` arguments have no revision-bearing counterpart to receive a pinned value distinctly from a repo id.
2. **`llm-behavior-eval` has no live `max_model_len` readback of its own** (items 6, 10) — closed at the wrapper level via a disposable-engine preflight (code-complete; requires GPU, not executed in this freeze).
3. **`repetition_penalty` is hard-pinned to `1.0`** for this evaluator family (item 15) — not a gap for this study, since `1.0` is the frozen intended value; flagged only so the constraint is explicit.
4. **Judge's own chat template thought-channel priming** (item 9 note) — a newly-surfaced, disclosed empirical risk to verify during smoke, not a code gap.

Item 3 (Uncensored Model LoRA adapter identity) is now **resolved**, not a
remaining gap — see `UNCENSORED_MODEL_ADAPTER_IDENTITY.md`.

None of these gaps were introduced by commits `361842c`/`83a814a`; items
1/2/6/8/10 are newly closed at the wrapper level by `preflight.py` (this
round).
